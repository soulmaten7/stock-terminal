# 기법 렌즈 개발 플레이북 & 문제해결 로그
> 목적: 기법(렌즈) 하나를 만들 때마다 반복되는 **문제·과정·교훈**을 기록. (1) 다음 기법에서 같은 함정·누락을 피하고, (2) 막혔을 때 "예전에 이 문제 어떻게 풀었지?"를 되짚어 추론하기 위함.
> **새 문제·해결이 생기면 아래 "문제해결 로그"에 계속 append 할 것.**

---

## 0. 관통 원칙 (절대 안 바뀜)
1. **예측기 아님 = 나침반.** 목표는 "정확한 예측"이 아니라 "정확한 해석 + 정직한 방향성 + 검증된 신뢰도". 미래가격·매수매도 단정 금지.
2. **"학습" = 재훈련(❌) → 맥락 검색+추론(RAG, ⭕).** 예측모델 훈련 함정(50~55%·과최적화) 회피.
3. **엔진 = 검증 일치.** 백테스트는 실제 `lib/*` 함수를 그대로 import해서 돌린다(구현과 검증이 다르면 무의미).
4. **데이터 먼저(garbage in, garbage out).** 결과가 약하면 "기법이 약하다" 결론 전에 **데이터 완전성·정확성·양**부터 감사.
5. **정직한 결과 그대로.** 검증에서 우위 없으면 억지로 "신호"라 안 함 → "건전성/위험/참고" 지표로 정직하게 두거나 뺀다. 세트를 부풀리지 않는다.
6. **하나씩 완전히.** 기법 1개를 5단계 끝까지 → 그다음 1개. 수익화·표시(껍데기)는 **모든 기법 검증 완료 후**.
7. **교훈은 조건부(맥락 의존) — "무조건 맞다" 금지.** 한 기법에서 통한 이론·데이터 처리·임계값이 다른 기법엔 다르게(또는 반대로) 적용될 수 있다. **같은 데이터도 기법마다 보는 시각이 다르다.** → 로그엔 "어느 기법/조건에서 배운 것"인지 함께 남기고, 다른 기법에 쓰기 전 "여기서도 같은가?"를 먼저 따진다. (예: "넓은 유니버스 필요"는 F-Score·저변동엔 결정적이지만 **모멘텀은 유니버스에 덜 민감** — 같은 교훈, 다른 적용. 예: `operatingCashFlow`는 F-Score에선 '이익의 질'이지만 REIT·자본집약 업종에선 다르게 읽어야 함.) 절대 원칙은 §0의 1~6만; 나머지(임계값·필드해석·유니버스 선택)는 기법별로 재검토 대상.

## 1. 기법 1개 개발 체크리스트 (5단계 + 감사 게이트)
1. **정의** — 규칙을 한 치 모호함 없이(canonical 버전). 임계값도 명시.
2. **데이터 매핑** — 필요 필드 목록 작성 → **정찰(probe)로 실제 소스가 주는지 확인**(추측 금지). 표시용 vs 검증용 소스 구분.
3. **엣지케이스** — 안 맞는 업종/상태 제외(은행=F-Score 미적용 등), 결측·0분모·상장 1년 미만 처리.
4. **검증(백테스트)** — **넓고 대표성 있는 유니버스**(대형+중형+소형) + point-in-time(미래 훔쳐보기 금지) + 엔진 재사용. 결과 정직 기록.
5. **표현** — 렌즈 카드에 라벨 + 근거 수치 + **정직 문구**(예측 아님·검증 결과·한계).
- **감사 게이트**: 4에서 결과가 약하면 → §데이터 감사(커버리지·필드 채움률·정확성) 먼저. 데이터 갭이면 소스/태그 보강 후 재검증.

- **가격(모멘텀·기술·저변동)**: 야후 `chart` — **수십 년** 깊이, 4개국(.KS/.KQ·.T·.HK/.SS/.SZ) 다 됨. 검증도 넓게 가능.

- **재무 — KR 검증용**: DART(무료·키 필요·다년) — 아직 미착수.
- **주의**: 은행·보험은 유동자산/부채·매출총이익 구조가 달라 F-Score류 미적용(정직하게 제외).

## 4. 재현 도구 (scripts/)
- `probe_*.mjs` — 소스가 필드를 주는지 정찰(구현 전).
- `backtest_momentum.ts` / `backtest_lowvol.ts` / `backtest_edgar.ts` — 다년 백테스트(엔진 재사용).
- `audit_data.ts` — 넓은 표본 데이터 커버리지·완전성·정확성 감사.
- 실행: `npx tsx scripts/<파일>` (TS import 때문에 node 말고 tsx).

## 5. 막혔을 때 (이 로그 사용법)
1. 결과가 이상/약하면 → §2 로그에서 비슷한 증상 검색(특히 #4 유니버스·#5 태그·#6 감사).
2. "기법 탓"이라 결론 내리기 전에 → §1 감사 게이트 통과했는지 확인(데이터 완전성·정확성·양).
3. 새 소스 붙일 땐 → 반드시 **정찰(probe) 먼저**(#1·#2 교훈).
4. 해결하면 → §2에 새 행 추가(문제·원인·해결·교훈·STEP). **교훈엔 "어느 기법/조건에서"인지 맥락을 붙인다.**
5. **로그 교훈 = 참고이지 정답 아님(§0-7).** 다른 기법에 적용 전 "이 기법 맥락에도 같나?"를 먼저 따진 뒤 쓴다(복붙 금지). 안 맞으면 그 차이도 로그에 남겨 → 지식이 더 정밀해짐.
