## §6 — 🔴 913 정정: "8일 정체"는 잘못된 열 판독이었다

### 913 §1 — `lens_cuts` 쓰기 주체 전수(파일을 직접 열어 확인, grep 매칭만으로 안 끝냄)

### 913 §2 — 07-28 04:33 = 씨딩도 정지도 아니었다: **트리거 없는 `updated_at`이 원인**

- `lens_cuts` 스키마를 직접 조회(`information_schema.columns`): `updated_at` 컬럼 default = `now()`. **`information_schema.triggers`에 `lens_cuts` 관련 트리거 = 0건.**
- `lensPrecompute.ts:394`의 upsert payload를 재확인: `{ market, lens_key, lo, hi, n, as_of: at, method }` — **`updated_at` 필드가 없다.**
- 🔑 **결론**: `updated_at`은 그 행이 **처음 INSERT된 순간에만** DB 기본값으로 찍히고, 이후 몇 번을 성공적으로 재-upsert해도 **다시는 안 바뀐다**(트리거도 없고 애플리케이션도 안 보내므로). **US·KR 10개 행 전부가 07-28 04:33:55.17017을 공유하는 이유는 "그때 다 같이 멈춰서"가 아니라 "그때 처음 만들어진 뒤로 그 컬럼만 아무도 안 건드려서"다.**
- **진짜 신선도 열은 `as_of`다**(애플리케이션이 매 실행 명시적으로 채움). 직접 10행 전부 조회: **US 5행 = `as_of` 2026-07-30 · KR 5행 = `as_of` 2026-08-04.** 🔴 **US=6일 전, KR=1일 전.** KR은 **정체가 아니라 정상**이었다.
- 대조군: `lens_scores`(값 테이블)는 upsert payload에 `updated_at: at`을 **명시적으로 포함한다**(`:253`·`:370`, 코드로 직접 확인) — 이 테이블의 `updated_at`은 신뢰할 수 있다. `us_market_cap`은 `updated_at`을 payload에 안 넣지만(`lens_cuts`와 동일 구조), `as_of`가 이미 그 목적으로 쓰였으므로 906·912의 `freshCoverage` 역산(5,401/5,966≈90.5%)은 **영향받지 않는다**(그 계산은 처음부터 `as_of` 기준이었다).

| 플랜 | Default | Maximum | Extended maximum |
|---|---|---|---|
| **Hobby** | 300s | **300s(= default, 확장 불가)** | 없음 |
| Pro/Enterprise | 300s | 800s | 1800s(베타) |

🔴 **Hobby는 300s가 기본값이자 절대 상한이다 — 늘릴 여지가 전혀 없다(공식 문서로 확정, 못 찾음 아님).**

**현재 설정 확인**(읽기만): `lens-scores`·`kr-lens-scores`·`us-perf` 세 라우트 전부 `export const maxDuration = 300;` — **이미 Hobby 절대 상한과 정확히 일치.** 여기만 보면 "여유 0"이라 A안 = 구조변경이어야 할 것 같다.

🔴 **그러나 "플랫폼 상한"과 "지금 이 라우트의 실제 소요"는 다른 질문이다.** 코드 주석(`app/api/cron/lens-scores/route.ts:7`) 및 기존 STEP 문서를 재확인:
- `route.ts:7` — *"실측 ~224초(상위 1000) → 300초 안."*
- `docs/STEP_833_COMMAND.md:38` — *"크론 실측이 상위 1000 계산에 ~224초/300초다."*
- `docs/STEP_834_COMMAND.md:46` — *"833 실측 소요 141s/300s이므로 별도 실행 1회는 가능."*

**두 실측(224초·141초)이 남아 있다 — 둘 다 300초보다 각각 76초·159초 적다.** 즉 라우트가 상한 300초를 다 쓴 적은 (기록상) 없다.

🔴 **다만 이 224초/141초는 Stage1(배치)+Stage2(재시도)+Stage3(폴백)+top-1000 렌즈계산 루프를 합산한 "라우트 전체" 시간이다.** 이번 STEP에서 서브에이전트로 `lib/lensPrecompute.ts`·해당 라우트 전수를 검색했으나, **`Date.now()`/`t0` 쌍은 파일 전체에 Stage2 재시도 가드용(:118, :121) 하나뿐** — 단계별(Stage1 vs Stage2 vs 나머지) elapsed 로깅이 코드에 전혀 없다. **"재시도 예산을 늘리면 정확히 몇 초의 여유가 남는지"는 계산할 수 없다.** 224초/141초라는 두 값 자체도 서로 83초 차이 나는 변동성을 보여, "여유가 76~159초"라고 폭을 좁혀 말할 수 있을 뿐 정확한 상수가 아니다.

🔑 **결론 — STEP §4의 이분법("여유 있으면 단순 증액" vs "여유 없으면 구조변경")에 정확히 들어맞지 않는다. 순수 "설정 한 줄"도 아니고, 곧바로 "구조 변경 필수"도 아니다:**
- Hobby **플랫폼 절대 상한**(300s) 자체엔 여유 0 — 확정.
- 그러나 **현재 라우트의 관측된 실제 소요**(224s/141s)는 300s보다 낮게 끝난 이력이 있다 — 재시도 예산을 40s→예컨대 70~90s 정도로 올려도 300s를 넘지 않을 여지가 산술적으로 있어 보인다.
- 🔴 **하지만 그 "여지"를 안전하게 계량할 계측이 코드에 없다.** Hobby는 Pro와 달리 300초를 넘기면 즉시 `FUNCTION_INVOCATION_TIMEOUT`(504)이고 확장 옵션이 전혀 없다(§4 표) — 계측 없이 예산만 올리면 나쁜 날(Stage1이 평소보다 오래 걸리는 날 등) 전체 실행이 300초를 넘겨 타임아웃날 위험이 있다(다만 `:154` 주석대로 100행마다 flush돼 상위분은 보존되므로 완전 유실은 아님).

**A안의 실제 형태(설계만, 🔴 구현 0)**:
1. **1단계 — 계측 추가**(동작 변경 없음, 리스크 0): Stage1/Stage2/Stage3/렌즈루프 각각의 elapsed를 `console.log`에 추가. 되돌리기 = 로그 줄 삭제, 즉시.
2. **2단계 — 계측값 기반 보수적 상향**: 며칠 치 실측으로 "재시도 외 나머지가 실제로 얼마나 쓰는지" 확인 후, 관측된 여유의 절반 이하로 `RETRY_MS`를 올린다. 되돌리기 = 상수 원복, 즉시.
3. **3단계(2단계로도 부족할 때만) — 구조 변경**: 여러 크론 호출로 분할(청크)·다회 실행. 되돌리기 비용이 1·2단계보다 확실히 크다(라우트·스케줄 재설계).

**한 번에 되는가**: 아니다 — 최소 1단계 배포 → 다음 실행(들) 로그 확인 → 2단계 조정, 최소 이틀 이상 걸린다. **되돌릴 수 있는가**: 1·2단계는 쉽게 되돌릴 수 있다(리버서블), 3단계만 구조적 비용이 있다.

## §14 — 935: 🔴 재시도 성공분 0건 — 대수적 도출이 아니라 구조적으로 성립함을 코드로 확인(진단만)

### 935 §1 — 대수적 도출이 성립하는가(코드 확인)

`lib/lensPrecompute.ts` 직접 재열람:

1. **재시도 성공분이 `freshSet`에 들어가는가** — `:131` `if (typeof q?.marketCap === "number" && q.marketCap > 0) { capOf.set(sym, q.marketCap); freshSet.add(sym); recovered++; }`. **들어간다**, `freshSet.add(sym)`과 `recovered++`가 같은 조건문 안에서 동시에 일어난다.
2. **`retryAll`의 계산 시점** — `:123` `const retryAll = [...noCapField, ...noResponse];`는 Stage1(배치) 직후·Stage2(재시도 루프, `:127-134`) **시작 전**에 확정된다. `freshCoverage`(`:135`, `freshSet.size` 사용)는 재시도 루프 **종료 후**. 🟢 **두 값은 같은 1회 실행(같은 함수 호출) 안의, 서로 다른 시점을 찍은 값**이다 — 다른 실행을 섞은 우연이 아니다.
3. **관계식**: `retryAllLen = STOCK_SYMS.length − batchOk`(정의상) · `freshSet.size = batchOk + recovered`(1·2에서 확인). 따라서 `STOCK_SYMS.length − freshSet.size = retryAllLen − recovered`는 **이 코드가 항상 성립시키는 항등식**이다(추측이 아니라 대입해서 나오는 식). 934가 측정한 두 값(`STOCK_SYMS.length−freshSet.size=511`·`retryAllLen=511`)을 대입하면 `511 = 511 − recovered` → **`recovered = 0`**.

### 935 §2 — 34.5ms/건의 정체

1. **재시도 1건이 실제로 하는 일**(`:127-133`): `mapLimit(retrySet, 6, ...)` 안에서 시간budget 체크(`:128`, 순수 로컬 시각 비교) 후 `yf.quote(sym)` — **실제 외부 HTTP 호출**. 즉시 반환하는 캐시·조건부 skip 경로는 **없다** — `timeHit=false`(933 실측)이므로 이번 실행에서는 시간 초과로 건너뛴 건도 0건, 400건 전부 실제로 `yf.quote()`를 호출했다.
2. **즉시 반환 경로 유무** — 없음(위 확인). 시간budget 초과 시의 `return`(`:128`)만 조기반환이며 이번 실행엔 발동 안 함.

항등식 재검산(이번 실행값, node 직접 실행으로 재확인): `freshSet.size = batchOk + recovered` = 5,509+0 = **5,509** · 분모 = 5,509÷0.9227805695142378 = **5,970.0000**(오차 없이 정수) · `retryAllLen` = 5,970−5,509 = **461**(관측값과 일치) · `noCapField(461)+noResponse(0)` = 461 = `retryAllLen`(일치). **934의 대수적 도출이 관측으로 뒷받침됐다** — 재시도 400건이 단 한 건도 복구하지 못했다.

### 937 §3 — 🔴 원인 축이 또 바뀐다: "실패"가 아니었다

관측된 사실만(해석 아님): `retryFailReasons:{}`(예외·에러 0건 — 429도 타임아웃도 5xx도 없음) · `retryFailSample:[]`(잡을 실패가 없었다) · `retryNoCapField:400`(재시도한 400건이 전부 정상 응답을 받았고, 그 응답에 `marketCap` 필드가 없었다) · `noResponse:0`(무응답 0) · `failedChunks/totalChunks:0/60`(Stage1 배치도 실패 0) · `batchOk:5,509`(배치가 5,509건은 정상 취득).

원인 축 이력: 912~934 *"예산(시간·개수) 문제"* → 935 *"취득 실패 가능성"* → **937 관측: 취득이 실패한 게 아니다.**

🔴 **여기서 원인을 확정하지 않는다.** 위는 관측이고, *"야후에 해당 종목의 시총이 없다"*는 해석이다. 축이 세 번 바뀐 이력을 고려해 해석을 결론으로 승격시키지 않는다 — 확정하려면 별도 검증(같은 심볼을 개별 `yf.quote`로 조회해 필드 유무 확인)이 필요하고 이 STEP의 범위가 아니다.

다만 934의 "불가" 판정과의 관계는 적을 수 있다 — 재시도가 에러 없이 같은 응답을 받는다면, 상한을 올려도 같은 응답을 더 많이 받는 것이라는 방향이다. **934의 판정을 뒤집지 않으며, 강화 방향으로 관측됐다는 사실만 기록한다.**

### 937 §4 — 나머지 계측 해석

**4-1. 935의 타이머 경계 문제 해소 — 933/934의 "34.5ms/건"은 오염된 값이었다.** `retryCallMs`(순수 재시도 호출)=5,703ms · `upsertMs`(DB 저장만)=7,377ms · 합=13,080ms=`stage2Ms`와 정확히 일치. 순수 재시도=5,703÷400=**14.3ms/건**(동시성 6 기준 실효 왕복≈86ms) — 933/934가 쓴 34.5ms/건은 DB 저장이 섞인 값이었다(935의 지적이 관측으로 확인됨). `timeHit:false`·`countHit:true` — 시간이 아니라 개수(400)에서 잘렸다(916의 반대 결론인 933이 이번에도 재확인).

**4-2. 커버리지는 개선됐으나 재시도 덕이 아니다.** `freshCoverage` 934시점 91.44%→937 92.28%(+0.84%p) · `retryAllLen` 511→461(−50) · `batchOk` 5,509 · 분모 5,968→5,970(+2). 개선분은 전부 Stage1 배치가 50건 더 성공한 것(`recovered`가 0이므로 재시도 기여 0). `data/us_symbols.json`이 매일 09:00 UTC 자동 갱신되므로 분모도 매일 바뀐다.

**4-3. 미시도분과 도달 상한(934 판정 재확인일 뿐, 재판정 아님).** 미시도 = `retryAllLen`(461)−`retrySetLen`(400) = **61건**. 전부 살린다고 가정: (5,509+61)÷5,970 = **93.30%** — 934가 다른 날 데이터로 계산한 값과 동일. 🔴 97% 임계 미달은 그대로.

**4-4. 구성 게이트도 미달 — 이번에 수치로 처음 관측.** `compositionOk:false`·`compRatio:0.93`(임계 0.95) — 커버리지(97%)뿐 아니라 구성(직전 상위 200 메가캡 fresh 확보율 95%)도 못 넘는다. 두 게이트 모두 실패라 `cutGateOk:false`.
