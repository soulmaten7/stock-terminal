## 1. 배경 — 1007 계측 설계의 실수

🔴 **내(Cowork) STEP 1007 설계 오류다.**
`revdcf`가 어디서 죽는지 재려고 heartbeat를 심었는데, **그 heartbeat를 `finally` 블록 맨 끝에 뒀다.**
함수가 강제 종료되면 `finally`도 안 돌기 때문에 **죽는 지점을 재려는 계측이 죽는 지점 뒤에 있었다.**

🔴 그리고 Vercel 로그가 403으로 막혀 외부에서 확인할 길도 없다.
→ **크론이 스스로 남기게 만드는 수밖에 없다. 죽기 전에.**

## 2. 할 일

### W1. `revdcf` 단계별 heartbeat — 죽기 전에 남긴다
`app/api/cron/revdcf/route.ts`

`finally` 블록 안에서 **단계가 끝날 때마다** heartbeat를 upsert한다(같은 `job='revdcf'` 행을 덮어쓴다 — 마지막에 성공한 단계가 남는다):

| 순서 | stage 값 | 찍는 시점 |
|---|---|---|
| 1 | `loop_done` | SEC 워커 루프 종료 직후, `finally` 진입 시 |
| 2 | `valuation_done` | `computeAndSaveValuation` 반환 직후 |
| 3 | `sector_relative_done` | `computeAndSaveSectorRelative` 반환 직후 |
| 4 | `complete` | 기존 위치(현행 heartbeat) |

각 단계 note에 **그때까지의 누적 경과시간**(`elapsedMsAtStage`)과 **`maxDuration` 대비 잔여**를 담는다.
🔴 **기존 note 필드는 전부 유지**한다(`finallyMs` 6구간 · `loopMs` · `budgetExhausted` · `sectorRelativeError` · `sectorRelativeSaved`). 이번 것은 **추가**다.
🔴 `recordHeartbeat`는 내부 try/catch로 격리돼 있어야 한다(917 §2). 4회로 늘어도 각 수십 ms라 부담 없음 — 🔴 **소요시간을 측정해 note에 담는다**(계측이 예산을 먹으면 본말전도).

🔴 **`BUDGET_MS`를 바꾸지 않는다.** 이 STEP은 **어디서 죽는지 보는 것**이지 고치는 게 아니다.

### W2. 나스닥 호출 방식 탐색 — 🔴 로컬만, 최대 5회
`scripts/probe_1018_nasdaq_call.ts`(프로브, 프로덕션 코드 아님)

현재 `lib/nasdaqMarketCap.ts`가 쓰는 호출을 기준으로 **아래를 순서대로 1회씩** 시도한다. **성공하면 즉시 멈춘다.**

1. **현행 그대로** (대조군 — 1017이 20,008ms timeout 확인)
2. **timeout만 60초로** — 응답이 느릴 뿐인가
3. **`download=true` 파라미터** — 나스닥 스크리너의 CSV/경량 응답 경로가 있는지 확인 후 시도
4. **페이지네이션 분할**(`limit`을 작게, 예: 1,000 × N) — 🔴 첫 페이지 1회만 시도해 응답 시간·크기를 잰다
5. **`exchange` 파라미터로 분할**(nasdaq/nyse/amex 각각) — 🔴 첫 거래소 1회만

각 시도마다 기록: **소요시간 · 응답 바이트 · 행수 · HTTP 상태 · 에러 사유**
🔴 **호출 간 10초 이상.** 🔴 **총 5회를 넘기지 말 것.**
🔴 **성공하는 방식을 찾았어도 이 STEP에서 `lib/nasdaqMarketCap.ts`를 고칠지는 아래 판정을 따른다.**

**교체 판정 규칙(이건 기계적이라 Claude Code가 적용해도 된다)**
- 🔴 **1회 성공만으로는 교체하지 않는다.** 성공한 방식을 **10초 간격으로 한 번 더**(총 2회) 확인해 재현되면 교체한다 — 그래도 총 호출은 7회 이내
- 재현 안 되면 **교체하지 말고** 결과만 기록한다
- 어떤 방식도 성공 못 하면 **교체하지 말고** ⓪-4 두 번째 갈래로 보고한다

교체할 경우:
- `lib/nasdaqMarketCap.ts`만 수정. 🔴 **`app/api/cron/us-perf/route.ts`의 try/catch 격리 구조는 그대로**
- 🔴 행수 3종 집계(응답/적재/빈 marketCap)와 실패 사유별 분류는 **그대로 유지**
