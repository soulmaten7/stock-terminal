## §1. 현재 상태 실측 (🔴 설계 전에)

| 재는 것 | 🔴 규칙 |
|---|---|
| `lens_scores` **현재 컬럼 전수** + 타입 | 이미 저장 중인 raw 필드가 있는지(반대증거 ㉠) |
| **현재 행수·시장별 분포** | US 998 외 KR 등 포함 전체 |

## §2. 무엇을 저장할지 확정 — 🔴 **네 사례에서 역산한다**

🔴 **필드를 상상해서 나열하지 않는다.** ⓪-1의 네 감사 문서를 열어, 각 감사가 **"이게 없어서 검산을 못 했다"**고 적은 것을 뽑아 그것만 후보로 올린다.

| 렌즈 | 그 감사가 「없어서 못 했다」고 한 것 | 필요한 컬럼(후보) | 타입·크기 추정 |
|---|---|---|---|
| 퀄리티 | | | |
| 기술 | | | |
| F스코어 | | | |
| 자산성장 | | | |
| (모멘텀 — `adjUsed`, STEP1084 실측) | 저장 컬럼 없음 | `adj_used` boolean | 1 byte |

🔴 **반대 증거 ㉢ 필수 확인**: 후보 중 **행 하나에 안 들어가는 것**(예: 원시 종가 252봉 시계열)을 골라낸다. 그런 건 `lens_scores` 컬럼으로 못 푼다 — **별도 테이블이 필요한지, 아니면 요약값(예: `ma200`·`pos52w` 결과값)만으로 검산이 성립하는지**를 각 감사 원문으로 판별한다.
🔴 **판별이 안 되면 "판별 불가 — 그 렌즈는 이 인프라로도 검산 불가"라 정직하게 적는다.**

## §3. 대가 실측 (🔴 이게 이 STEP의 핵심)

| 항목 | 재는 법 | 🔴 규칙 |
|---|---|---|
| **저장용량 증가** | §2 후보 필드 합계 bytes × 현재 행수 | 🔴 산술임을 명시 · 현재 테이블 크기 대비 **몇 %**인지 |
| **쓰기 경로 영향** | `lensPrecompute.ts`가 upsert하는 지점 — 컬럼 추가 시 코드 변경 범위 | 🔴 **코드 읽기만**, 안 고침 |
| **읽기 경로 영향** | `lens_scores`를 읽는 소비처 전수(`select *` 쓰는 곳이 있으면 페이로드 증가) | 🔴 소비처 좌표 나열 |
| **마이그레이션 방식** | `ALTER TABLE ADD COLUMN`(nullable) 초안 | 🔴 **문서 안 코드블록으로만.** `supabase/migrations/` 파일 **생성 금지** |
| **백필 필요 여부** | 기존 998행을 채울 것인가, 다음 크론부터 채울 것인가 | 🔴 백필하려면 크론 재실행이 필요한지 확인(수동 실행은 금지) |

🔴 **용량이 현재 테이블의 2배를 넘으면 그 사실을 굵게 적고, ①을 그대로 진행할지 재확인이 필요하다고 표시**한다(멈추라는 뜻이 아니라 **눈에 띄게** 적으라는 뜻).
