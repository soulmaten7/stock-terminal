# 실수 기록 (mistakes)

> 재발 방지를 위한 누적 기록. 새 항목은 여기 추가한다(옛 `docs/LENS_DEV_PLAYBOOK.md`의 "문제해결 로그" 역할을 승계 — 단 그 문서는 읽기 참조로 유지, 새 항목은 여기로). 형식: **무엇이 틀렸나 / 왜 / 어떻게 알았나**. 짧게, 조건부로("이 조건에선…") — "무조건 맞다"로 일반화하지 않는다.

---

## 2026-09-05 배운 것

- **서비스롤(비밀) 키는 채팅·명령어에 직접 붙이지 않는다 — 파일 편집기로 넣는다.** `read -rs NEW_K...` 방식으로 셸에서 값을 받아 붙이려다 두 파일(`.env.local`·stock-shorts `config/.env`)에서 셸 히스토리 잔재가 실제 키 값과 꼬여 붙는 사고가 났다(`SUPABASE_SERVICE_ROLE_KEY=read -rs NEW_K...sb_secret_...` 형태로 오염). 복구는 가능했지만(양쪽 오염 패턴 대조로 원래 값 역추정 후 curl로 검증) 애초에 셸 인자·대화 로그에 비밀 값이 스치지 않게, 파일을 직접 열어 편집하는 방식으로 넣어야 한다. **적용**: 키·토큰 교체 요청이 오면 `read -rs`/echo 파이프 대신 Edit 도구로 파일을 직접 고친다.
- **"모델을 다 걷어냈다"는 인식만으로 크론을 끄지 않는다 — 전수 조사 없이 "다 됐다"고 판단하면 살아있는 소비처를 놓친다.** 모델 잔재 전면 제거(85356be) 직후 "이제 렌즈 크론도 끌 수 있겠다"고 생각했으나, 실제 전수 조사(`lens-cron-consumers-audit` 포크)에서 홈의 "내 관심종목·렌즈 변화" 섹션이 `lens_state_changes`를 그대로 쓰는 라이브 소비처로 남아있었다 — 화면 잔재 제거와 데이터 소비처 제거는 별개 질문이라, 화면을 치웠다고 곧장 크론을 끄면 안 됐다. **적용**: 크론·API·테이블을 정지하기 전에는 "이 산출물을 지금 읽는 코드가 남아있는가"를 grep으로 전수 확인하고, 라이브/파킹/죽음 상태를 소비처 단위로 분류한 뒤에만 정지한다.
- **명령서(ORDER) 표에 빈칸을 남기지 않는다 — 실행자가 채우게 되면 그 자체가 임의 결정이 된다.** 판단이 안 끝난 항목을 빈칸이나 "TBD"로 두고 넘기면, 실행 단계에서 누군가(사람이든 에이전트든) 자기 판단으로 채우게 되고 그게 사실상 미승인 결정이 된다. **적용**: 명령서 표는 셀을 전부 채우고 낸다 — 정말 미정이면 빈칸이 아니라 "확정 대기(사유)"라고 명시해, 실행자가 자기 판단으로 채우지 못하게 한다.

## 2026-09-07 배운 것

- **fire-and-forget 트리거에서 pg_net 기본 타임아웃(5초)이 실제 처리시간보다 짧으면, 성공도 timeout으로 로깅돼 진짜 실패와 구분이 안 된다.** `channel_growth_stories`/`channel_reports`의 AFTER INSERT(OR UPDATE) 트리거가 `net.http_post()`로 번역 API를 비동기 호출하는데, 이 함수의 `timeout_milliseconds` 기본값은 5000이다. 실제 처리(원문 조회 + OpenAI 번역 호출 + 저장)는 6~8초 걸려서, `net._http_response`에는 **성공한 호출도 실패한 호출도 똑같이 `status_code: null, error_msg: "Timeout of 5000 ms reached"`**로만 남았다 — 트리거 자체 동작(Vercel 함수는 서버에서 계속 실행돼 정상 완료)엔 영향이 없었지만, 로그만 보고는 "이번 호출이 진짜 실패했는지" 전혀 판단할 수 없는 상태였다. 어떻게 알았나: `channel_growth_stories` 8건에 무해한 UPDATE로 트리거를 재발화해 실측 — 8건 다 `net._http_response`는 timeout으로 찍혔는데 `channel_growth_story_translations`엔 8건 다 `status='ok'`로 정상 저장돼 있어 모순을 발견. **적용**: `net.http_post()`를 쓰는 모든 fire-and-forget 트리거는 `timeout_milliseconds`를 관측된 실제 처리시간보다 충분히 크게(이번엔 15000) 명시한다 — 기본값 5000을 그대로 두면 안 된다. 수정 후 재발화로 `status_code: 200`이 찍히는 것까지 확인해야 로그를 다시 신뢰할 수 있다.
